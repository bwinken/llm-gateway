# CLAUDE.md

Guidance for Claude Code (claude.ai/code) in this repository.

OpenAI- and Anthropic-compatible reverse proxy in front of on-prem vLLM servers, Azure OpenAI and AWS Bedrock, with per-user API keys, budgets, concurrency limits and usage billing. FastAPI + httpx + SQLModel/PostgreSQL + Jinja2.

This file is the map and the rules. **[docs/architecture.md](docs/architecture.md) is the reference**: read the section for a subsystem before changing it. When you change behavior, update that section; when you add a rule someone could easily break, add a line under *Rules* below.

## Commands

```bash
uv sync                                    # install
uv run fastapi dev app/main.py             # run with auto-reload
uv run pytest tests/ -q                    # all tests (CI runs the same)
uv run pytest tests/test_messages.py::TestX::test_y -v   # one test
uv run ruff check . [--fix]                # lint (CI runs the same)
uv run alembic upgrade head                # apply migrations
uv run alembic revision --autogenerate -m "description"
uv add <package>                           # add a dependency (commit uv.lock too)
```

## Request flow

```
Client (API key) → deps.py: auth, [IP allowlist], daily limit, [concurrency slot]
   /v1/*        → v1_api.py: alias in AZURE_MODELS + can_use_azure     → azure_proxy   (→ Responses API)
                             alias in BEDROCK_MODELS + can_use_bedrock → bedrock_proxy (→ Converse API)
                             otherwise                                 → [guardrail] → vllm_proxy
   /azure/v1/*  → azure_api.py  → azure_proxy   (require_azure_access)
   /aws/v1/*    → aws_api.py    → bedrock_proxy (require_bedrock_access)
   → downstream → _log_usage() → usage_logs + Langfuse (no-op unless configured)
```

Admins bypass the Azure/Bedrock flags. Every route also exists without the `/v1` prefix. Naming split: the URL prefix is **`/aws`**, but config, flags and the backend tag all say **`bedrock`** (`[bedrock_models.*]`, `can_use_bedrock`, `backend="bedrock"`).

## Rules

Each of these has broken production or a test before. The parenthesized test pins it.

**DB connections and request lifetime**
- API-path auth dependencies open their **own short-lived session** (`with Session(engine)`), never `Depends(get_session)`. A `yield` dependency's exit runs after the response is sent, streams included, so a request-scoped session pinned one pool connection per open stream and exhausted the QueuePool (`test_auth_session_scope.py`). The web/admin routers may keep `Depends(get_session)`.
- That same exit timing is what keeps a concurrency lease held for a whole stream. If a FastAPI upgrade ever changes it, the limit silently stops limiting (`TestLeaseSpansTheResponse`).
- Teardown that runs on client disconnect must survive anyio's repeated cancellation: detach it (`_release_stream`) or shield it (`anyio.CancelScope(shield=True)`). Otherwise connections and leases leak (`test_stream_disconnect_cleanup.py`, `TestClientDisconnect`).
- Never hold a DB connection across a stream: no advisory locks, no long transactions.
- A web/admin handler that queries the DB and never `await`s is a plain `def` (FastAPI's threadpool). An `async def` running a `usage_logs` aggregate blocks the event loop and stalls every stream on the worker (`TestReportPagesRunOffTheEventLoop`).
- Every timestamp field in `schema.py` is typed `NaiveDatetime` (columns are `timestamp without time zone` holding UTC). sqlmodel ≥ 0.0.48 maps a plain `datetime` to a timezone-aware type that rejects naive values and changes the DDL, so a plain `datetime` field breaks every insert and makes `alembic check` report drift.
- Select app accounts in SQL with `schema.app_account_clause()`, never `User.username.startswith("app_")`: that compiles to `LIKE 'app_%'`, where `_` is a wildcard (`TestAppAccountClause`).
- `delete_user` clears every row referencing `users.id` before deleting the user: `app_owners`, the legacy `users.owner_id`, `anomaly_events`, leases. It **keeps** `usage_logs` and `usage_daily` (billing / audit record; deleting one but not the other makes reports disagree) and logs the id → account mapping. Code reading usage must tolerate user ids with no account (`TestDeleteUser`, the deleted account in `test_usage_rollup.py::history`). Add any new FK there too; PostgreSQL turns a missed one into a 500 that SQLite tests miss unless `PRAGMA foreign_keys` is on (`TestDeleteUser`).

**Usage reports**
- Report days and months are **Asia/Taipei** calendar days and months (`timeutil.local_today`, `local_month_start`, `local_day_start_utc_of`), never UTC months.
- Any figure spanning more than today reads through `usage_rollup.aggregate`, never a new `usage_logs` range scan: that scan is what made `/admin` slow as traffic grew. Today-only figures may query `usage_logs`. Every report must give the same numbers whether the rollup has run or not (`TestSameNumbersEitherWay`).
- Only the rollup writes `usage_daily`, never the request path: a per-request upsert would make one user's concurrent requests contend on the same row. Days after the watermark are read from `usage_logs`, so the rollup being off or behind costs speed, never correctness.
- Never DISTINCT-count users per day in SQL over request rows (`count(DISTINCT user_id) ... GROUP BY day` sorts every row); count `(day, user_id)` groups (`stats.count_daily_active`).

**Periodic jobs**
- Periodic work runs inside the gateway, never as a systemd timer or cron entry: a `scheduler.Job` started by `job_loop` in the lifespan, claimed per interval in `scheduled_jobs` (exactly one worker runs it), body in a thread with its own session, never raising into the app. The rollup is the one exception with its own loop (per-day advisory lock) (`tests/test_scheduled_jobs.py`).
- A job holding the shared pool keeps its statements bounded with a transaction-scoped `SET LOCAL statement_timeout`, never a session-level `SET` (that would leak into the pooled connection).
- Retention never deletes past the rollup watermark and only whole local days: a raw row not yet in `usage_daily` would vanish from every report. It stays off unless `USAGE_LOG_RETENTION_DAYS` is set (`TestRetention`).
- Anomaly findings for accounts that no longer exist are dropped before persist: `anomaly_events.user_id` is a foreign key and usage of deleted accounts is kept.

**Streams**
- Every streaming pre-flight uses `_STREAM_TIMEOUT` (time-to-headers is bounded) and checks `status_code` **before** handing the response to the pump. A cloud 4xx is a JSON body that the pump would silently drop (`test_stream_preflight_timeout.py`).
- Ping heartbeats are injected only at SSE event boundaries. OpenAI-shape streams consume the idle ticks silently.
- An Anthropic stream that ends without `finish_reason` emits `overloaded_error` (Claude Code retries it), never `message_stop`.
- Failover or rate-limit fallback may switch servers only before the client has received a byte.

**Side effects never break a request**
- Billing (`_log_usage`), Langfuse, Prometheus metrics, slow-request logging and the concurrency store are wrapped so their failure can't fail the request. The concurrency store fails **open**. The blind `except Exception` around them is intentional.
- Every user-traffic httpx client is built with `event_hooks=UPSTREAM_EVENT_HOOKS` (phase timing); the health client is not. A new client without them silently drops `gateway_overhead_ms` / `upstream_ttfb_ms` for its backend (`test_request_timing.py`).
- `_log_usage` is the single billing and observability seam. Debug and metadata calls (`render`, `tokenize`, `count_tokens`) must never reach it.
- Prometheus labels never carry a user identity or a client-sent string: `model` goes through `metrics._model_label` (unknown → `other`). Per-user numbers belong in `usage_logs`, not in a label (`test_unknown_model_is_reported_as_other`).
- The Langfuse `usage_details` always carries an explicit `total` = input + output. `input` already includes the cached tokens, so without it Langfuse sums every key and counts cache reads twice (`TestSystemOneObservability`).

**Routing and config**
- Aliases are unique across `[models.*]`, `[azure_models.*]` and `[bedrock_models.*]`. `_build_config` raises at startup; `PUT /admin/api/config` rejects collisions before writing.
- An unknown alias falls back (with `X-Model-Fallback`) rather than returning 404. A cloud alias requested without permission silently falls back to vLLM: cloud models are hidden through the `/v1/models` filter, not through errors.
- `GET /v1/me` authenticates with `get_current_user_unmetered`, never `get_current_user`: it must answer when the budget is spent, which is when clients ask (`TestOverBudget`). Its response never contains `null` (`_no_nulls` in `test_account_info.py`).
- Every account has a limit: `daily_limit_usd = 0` is a **$0 budget**, never "unlimited", and a cloud cap of `0` refuses cloud (absent = no cloud cap). Admin writes go through `admin._limit_usd` (finite, ≥ 0); never reintroduce a `<= 0` → skip branch (`TestZeroLimit`, `TestAdminLimitValidation`).
- An exhausted cloud cap is a **429**, not a silent vLLM fallback, unless `[app].cloud_budget_fallback` is on, and that only applies on `/v1/*`.
- Cloud spending has **one** cap for Azure + Bedrock together: a user's own `users.cloud_daily_limit_usd`, whose NULL means **follow `[app].cloud_daily_limit_usd`**, not "no cap". Read it only through `deps.effective_cloud_limit`. It only applies to users with Azure or AWS access. Don't reintroduce per-backend amounts: `azure_daily_limit_usd` / `bedrock_daily_limit_usd` are retired and unread, and the admin API 400s those fields (`tests/test_cloud_limit.py`).
- `rate_limit_fallback` stays on the **same backend**, and the request body is rebuilt per attempt from a deep copy of the original.
- Reasoning effort: no nearest-level guessing. Forward what was asked, what config maps it to, or nothing. An undeclared route is byte-faithful. `max` is a level of its own, not a spelling of `xhigh`. `reasoning_effort` is only emitted for `is_reasoning` models.
- Thinking history replayed downstream carries **both** `reasoning` and `reasoning_content` (vLLM ≥ 0.20 reads only the former).
- System messages appear only at index 0. Mid-conversation system/developer entries merge into the adjacent user turn as `<system-reminder>` text: hoisting them would break prefix caching.
- Every page that lists models sorts them with `app/services/model_order.py` (type, the backend's `[display_order]` list, price, natural alias order), Cost by Model included: never add a list with its own sort. `admin_models.html` mirrors it in `displayOrder`; change both together (`tests/test_model_order.py`).
- New per-model config keys go in the right tuple: `_MODEL_METADATA_KEYS` (surfaced in `/v1/models`), `_MODEL_PRICING_KEYS`, `_MODEL_REASONING_KEYS`, or the internal/cloud-routing keys (never surfaced).
- `/readyz` gates on the database only. The vLLM health cache is per-worker and failing on downstream outages would pull every instance out of the load balancer at once.

**Security and logs**
- Never log raw request bodies. Use `redact.summarize_body()` (shape only); `LOG_REQUEST_BODIES=true` is a debugging escape hatch.
- CORS never sets `allow_credentials=True`: Starlette echoes any `Origin` on cookie-carrying requests, and with that header it would hand admin responses (full API keys included) to other sites. SSO-authenticated writes live under `/admin` or `/dashboard`, where `CrossSiteRequestGuard` refuses cross-site requests; a new prefix goes in `COOKIE_AUTH_PREFIXES` (`tests/test_browser_security.py`).
- API keys are issued only by `schema._generate_api_key` (256 random bits). Never reject an older-format key by its shape: auth is an exact lookup and existing keys must keep working; `is_legacy_api_key` only drives the dashboard nudge and the admin filter (`tests/test_api_key_hardening.py`).
- (Re)issue a key only through `schema.issue_api_key` (it resets `api_key_created_at` / `api_key_last_used_at`). Last use is stamped from `deps._authenticate` at most hourly per user per worker, after the auth session closed, never per request (`tests/test_key_last_use.py`).
- The failed-auth throttle counts **distinct** invalid keys per address and, once locked, refuses before the key lookup. Counting attempts instead would let one stale client lock out a whole office NAT; looking the key up while locked would let a guesser keep testing (`TestThrottle`).
- Admin listings show `mask_api_key(...)`. Full keys come one at a time from `GET /admin/users/{id}/api-key`, which is logged.
- Admin-editable site links accept only `http(s)://` or site-relative URLs.
- Downstream error lines include `user`, `model`, `endpoint` and the exception **type**. httpx timeouts stringify to an empty message.
- A client never sees a downstream exception's text (internal hosts and URLs): 502 details and mid-stream error events go through `redact.downstream_error_detail` (type only); the full text goes to the log (`TestClientSeesNoInternals`).
- Converse 400s a sampling field a model lacks instead of ignoring it, and which models do differs per family (OpenAI GPT, gpt-oss, Kimi, GLM). Don't add a per-family table: every Converse call goes through `bedrock_proxy._send_converse`, which drops the field Bedrock names (`temperature` / `topP` / `stopSequences` only), retries before the first byte and remembers it per `model_id`. Reasoning effort is the one family-shaped field: flat `reasoning_effort` for gpt-oss, nested `reasoning.effort` for the GPT models (`tests/test_bedrock_unsupported_fields.py`).
- Bedrock bodies go out as `content=_encode_body(...)`, signed by `_build_headers` over those exact bytes. Passing `json=` re-serializes the body and breaks every SigV4 signature (`test_iam_credentials_sign_with_sigv4`).
- The Bedrock-native Messages path never forwards the client's `anthropic-beta` header, and drops the beta-only body fields with it (`_NATIVE_TOP_LEVEL_KEYS`): Bedrock 400s a beta it does not serve, which would fail every Claude Code request. Billed input there is `input_tokens` + cache reads + cache writes, because Anthropic's `input_tokens` excludes both (`test_bedrock_native_messages.py`).

**IP allowlist**
- The check needs the account, so it runs inside `deps._authenticate` (called with the request by `get_current_user` / `get_current_user_unmetered`), right after the key is resolved. Every API route must authenticate through one of those two, or it skips the allowlist (`TestEveryApiRouteIsChecked`). Never add it to the web UI, admin, OAuth or health paths: the admin page that edits the list must stay reachable from an unlisted address, and the load balancer must keep seeing `/readyz` (`test_web_ui_and_health_are_never_gated`).
- A rule admits an account by username or org code (both empty = everyone). Store usernames and org codes, not user ids: deleting an account must never touch `ip_allow_rules`. Adding and editing go through `validate_who`, which refuses unknown names (`test_unknown_accounts_and_org_codes_are_refused`).
- The client address is `request.client.host` (uvicorn's proxy headers, trusting `--forwarded-allow-ips`). Never read `X-Forwarded-For` / `X-Real-IP` yourself: the leftmost hops are whatever the client sent.
- The request path reads the per-worker snapshot only, never the DB. Anything that writes `ip_allow_rules` calls `ip_allowlist.refresh()` afterwards; the other workers catch up within `REFRESH_S` (`test_ending_a_rule_early_applies_after_the_refresh`).
- Only admins create, edit or end rules. Users get no way to open access themselves (no dashboard control, no endpoint) and the dashboard never shows them their address (`TestNoUserSelfService`). `created_by` is a username, not a foreign key.
- A new account permission column is also a `status` filter and a *Special access* chip: add it to `admin._status_clause`, `USER_TABLE_STATUSES` and `SPECIAL_ACCESS_KEYS` (and to the `special` clause), or the overview silently misses it (`TestSpecialAccess`).
- Settings are read through `ip_allowlist.settings()`, so the conftest's one patch keeps the allowlist off in every test.

**Guardrail**
- The guardrail screens local (vLLM) traffic only, right before the `vllm_forward_*` call in `v1_api` (so cloud-budget fallbacks are screened too). Never add it to the Azure / Bedrock paths (`tests/test_guardrail.py::test_cloud_traffic_is_not_screened`).
- It fails **open**, even in `block` mode: timeout, HTTP / connection error or an unparsable reply lets the request through, recorded as `guardrail = timeout | error | parse_error`. The default action is `monitor` (never refuses) (`TestEvaluate`, `test_block_mode_fails_open_on_timeout`).
- The guard call is never billed: it must not reach `_log_usage`, and it uses `get_guardrail_client()` without `UPSTREAM_EVENT_HOOKS` so it doesn't count as the request's upstream (`test_monitor_passes_and_records`).
- The parser is Qwen3Guard-Gen's (`Safety:` / `Categories:`). Changing the guard model means rewriting `build_guard_request` / `parse_qwen3guard`; the admin card says so.
- A blocked request records its own Langfuse generation (it never reaches `_log_usage`); every other screened request carries the verdict on its normal generation via the request-meta contextvar. Never log the screened text.
- Only `block` waits for the verdict. `monitor` runs the guard as a background task alongside the vLLM call, and the request's Langfuse generation is deferred until the verdict is in (`PendingVerdict.add_done_callback`). Never block a thread or the loop waiting for it: the executor threads also carry the `usage_logs` writes (`test_monitor_does_not_wait_for_the_guard`, `test_monitor_langfuse_generation_waits_for_the_verdict`, `test_block_mode_judges_before_forwarding`).

**Client rules and mail**
- No backend returns Claude Code's server-side auto mode verdict. Never answer it from the gateway (a made-up verdict turns the safety check off while the user believes it is on); check `CC001` tells the user the client-side fix instead.
- What a client rule detects is code (`client_checks.CHECKS`), never admin input and never database content: don't add condition fields to the admin form or judgment columns to `client_rule_settings`; a threshold is a constant in `client_checks.py` (`MIN_CLAUDE_CODE_VERSION`). The database records violations by id and how each check's accounts are told, nothing else (`test_thresholds_are_code_not_settings`). A new check gets the next unused id and a test in `TestChecks`; a check leaves in two steps, both in code: `deprecated` (still recorded and shown, but never reminds or mails; every reminder and mail path checks `rule.deprecated`), then `retired` (not evaluated, listed under *Retired*); never delete an entry or reuse its id (ids are in `client_violations` and in mail people received) (`TestRegistry`, `TestLifecycle`). `detect` runs on every Messages request: no I/O, config only through `app.core.config` getters, and it reads whether a body field is present or `model`, never the conversation.
- A new Messages route calls `client_rules.observe_request` and returns its response when there is one, or its users get no notices, reminders or version record (`test_cloud_messages_routes_are_watched_too`).
- The request path reads the per-worker snapshot and writes at most hourly per account. Nothing there may fail a request except a due reminder, which an admin chose per check: a broken store or a check that raises finds nothing (`test_a_broken_store_never_fails_the_request`, `test_a_check_that_raises_finds_nothing_and_spares_the_others`). Anything that writes `client_rule_settings` calls `client_rules.refresh()`.
- The `CC002` (plain http) check reads `request.url.scheme`, never `X-Forwarded-Proto` itself: the client can send its own (`test_plain_http_is_the_connections_scheme_not_a_header`).
- A settings patch only sets or removes variables in the `env` block of settings.json: `parse_env` cannot express anything else, and the script must never touch the rest of the file. Don't widen it to arbitrary settings. It reaches the user's machine as base64 inside `render_patch_bat`: never interpolate admin text into the `.bat` outside `_bat_text`, and keep every runtime's part doing exactly `apply_env` (`_NODE_APPLY`, shared by the `.bat` and the `.sh`; `_PYTHON_APPLY`; the PowerShell block). The Node and Python parts are run by the tests; the PowerShell part is not, so change it with care (`TestPatch`).
- A check whose fix is a setting declares `needs_patch`, and `clean_fields(form, check)` refuses turning it on with an empty *Everyone* patch (the form stops it first, the server is the guard); don't enable such a check by default without a default patch (`test_a_check_cannot_be_turned_on_without_its_patch`).
- A setting everyone should have but no request reveals (model discovery) is not a check: it goes in `client_checks.BASELINE_ENV`, which `effective_env` adds to every non-empty patch, the check's own value winning (`TestBaseline`).
- Which patch an account gets is decided in one place, `effective_env` (base, then Azure, then AWS on top, then the baseline): the dashboard text, the download and the mail must all go through it (`test_the_patch_follows_the_accounts_access`, `test_each_recipient_gets_the_patch_for_their_access`).
- An account is told once about everything it has open, never once per check: mail is built per account from `open_items` (`_send_digests`, `render_digest`) with one patch from `combined_env`, and the dashboard offers the same patch for all its notices. Don't add a per-check send. Where two checks set one variable the later check wins, and `env_conflicts` must keep telling the admin (`TestOneMailPerAccount`, `TestEverythingAtOnce`).
- An account has **one** patch download, `/dashboard/client-rules/all/patch.{bat,sh}` (`combined_for`, one notice or several), and the mail links to that same URL: don't add a download per check or put a patch in a mail attachment. The panel and the mail say which checks the script cannot fix (`split_covered`); keep that when adding a check without a patch. The panel is `_client_notices.html`, rendered in the dashboard and alone by `GET /dashboard/client-notices`: change it there (`test_there_is_no_download_per_check`, `test_the_panel_says_what_the_script_does_not_cover`, `test_the_mail_links_straight_to_the_one_patch`).
- The API key patch (`GET /dashboard/api-key/patch.*`, `key_env`) sets `API_KEY_ENV` (`ANTHROPIC_AUTH_TOKEN`) to the caller's own current key, removes `API_KEY_ENV_RETIRED` (`ANTHROPIC_API_KEY`) and nothing else. The key lives in that one variable: don't write it to a second one in the installer, a patch or the setup page (a copy goes stale on the next regenerate). A key never goes into a notice's patch, into mail or into `BASELINE_ENV`, and the script never prints it; the download stays in `audit._AUDITED_READS` (`TestKeyPatch`).
- Mail goes out paced, never as a burst (a mail server may read one as abuse): every send path is `send_due`, one batch per run (`mail_pace`: batch, pause, interval, all from `.env`). An admin's click only queues (`request_mail` for one check's accounts, `request_mail_all` for everyone with anything open; both go through `_queue_accounts`, which stamps `mail_requested_at` on everything the account has open, so every check's list shows it queued) and triggers one batch; never loop over a whole list of recipients, and keep the compare-and-set claim in `_send_digests` that stops two senders mailing one account (`TestPacedMail`).
- A violation counts for `WINDOW_DAYS` (15) after it was last seen; an account quiet for longer is left alone and comes back as a new case (`_touch_violation` resets its mail and resolved state). Reminders, per-check or monthly, only go to an account seen violating since its last mail (`TestQuietAccounts`, `TestMonthlyReminder`).
- Whether a violation still counts is `client_rules.is_resolved` (the account pressed *I've applied it* and has not violated since), never a deleted row or a compliant request: one clean request proves nothing when the account has a second machine. Notices, mail targets and the admin's open counts all go through it, and a new violation reopens it by moving `last_seen_at`; that reopening also clears the row's mail state (a new case: it is mailed again), keeping `resolved_at` for the admin's *open again* label (`TestResolved`).
- Violations and versions store usernames and check ids, not foreign keys, so `delete_user` and retiring a check leave them alone; readers skip names without an account (`mailable`).
- Every mail attempt is written to `client_mail_log` by `client_rules.record_mail` (address, checks, why, sent or failed with the error), test mail included: a new send path calls it too, after the send, and it never raises, so a broken log cannot stop or undo a mail. The row holds no mail body, and nothing updates or deletes rows (`TestMailLog`).
- Mail settings come from `.env` only (`mailer.settings`), never from the admin UI or `config.toml`; test mail goes to the company domain only; `mailer.send` is blocking and never raises, so call it from a thread, never the event loop (`TestMailer`, `TestMail`).
- Text an admin writes (title, message, patch) is escaped wherever it is shown: Jinja autoescape on the pages, `html.escape` in `render_mail` (`test_mail_escapes_what_the_admin_wrote`).

**Audit log**
- Audit coverage comes from `AuditMiddleware`, not from handlers: never replace it with per-endpoint calls, and keep new SSO-authenticated writes under `/admin` or `/dashboard`. A new read that reveals credentials or exports data goes in `audit._AUDITED_READS` (`tests/test_audit_log.py`).
- Nothing updates or deletes `audit_log` rows (PostgreSQL triggers refuse it). It stores usernames, never user ids, so `delete_user` leaves it alone.
- Secrets never reach it: request and reply fields go through `audit.redact`; a handler whose body is too large or sensitive is added to `_BODY_NOT_RECORDED` and notes a summary instead (`PUT /admin/api/config` notes `config_changes`, field names only).
- The write never fails the request; a failed write logs the whole record.

**Admin UI**
- In-place actions POST with `Accept: application/json` and repaint one element; without that header `fetch` follows the 303 and the server renders the whole admin page for nothing. Send explicit values (`enabled=on|off`): disabled controls are dropped from `FormData`. Use `gwToast` / `gwConfirm`, never `alert()` / `confirm()`.
- The Users and Apps tables are one partial, `_admin_user_table.html`, with one row macro: change a column there, not in two copies. It renders inside `/admin` and alone from `GET /admin/user-table`, both from `_user_table` and the same query parameters. Links into it are built by `_admin_url` (URL-encoded), never by interpolating `q` into an `href` (`tests/test_admin_users_panel.py`).
- `/dashboard` and `/admin` split their lower half into tabs via `gwTabs(barId, storageKey)` in `base.html`: buttons `data-tab="x"`, panels `data-panel="x"` (several panels may share a name). The active tab comes from the URL hash, else `sessionStorage`. The fallback is required because every admin form POST redirects to plain `/admin`, dropping the hash. Above the tab bar sit only the dashboard's budget hero and the admin's "Needs attention" strip, a `<details>` that is one line of counts when folded: open on Overview, folded on the other tabs (it follows the `gw:tab` event `gwTabs` fires) so the tab bar is on screen when the page opens; don't put anything taller there. Admin tabs group cards by purpose: Overview (key numbers, usage), Users (accounts, create app account), Clients (client rules), Security (IP allowlist, guardrail, audit log), Settings (gateway-wide limits, site links); put a new card on the tab it belongs to (`test_each_admin_card_is_on_the_tab_it_belongs_to`). Charts inside a hidden tab are sized on the `resize` event the switch fires. The admin bar is the shared partial `_admin_tabs.html`: its last tab, **Models**, is a link to the separate `/admin/models` page, which renders the same bar with links back to `/admin#<tab>`. Model Config is deliberately not embedded: its URL hash is the model selection (`#settings` would collide with the admin tab of that name) and its unsaved-changes guard must keep firing on navigation.
- Render pages with `templates.TemplateResponse(request, "name.html", context)`: starlette ≥ 1.0 (pinned `>=1.3.1` for its security fixes) no longer takes the template name first, and the old call order is a 500.
- `admin_models.html` writes every input straight into its `config` object through `setField`. There is no DOM re-collection at save time.
- `GET /admin/api/config` sends model secrets as `<stored:section/alias/field>` references, never values; `PUT` and *Test connection* resolve them. A new secret config key goes in `config.SECRET_FIELDS` (`tests/test_config_secrets.py`).

**Backups**
- An encrypted backup never leaves plaintext behind: verify the dump, encrypt it, delete the plaintext, and only then `mv` the `.gpg` into place. In-progress files start with `.` so the monthly copy and pruning (which glob `llm-gateway-*`) never take one for a backup. The gateway host holds the public key only; nothing there may need the private key.
- `restore-drill.sh` removes its container with `docker rm -f -v`: without `-v` the image's data volume survives even a `--rm` container, leaving a full restored copy of the database on the host. Every run, failed ones included, appends to the drill log; that line is the audit evidence.

**Lint and config**
- Ruff's rule set is deliberately narrow (`E4`, `E7`, `E9`, `F`). Don't widen it: the default set fights intentional patterns such as blind excepts and `Depends()` defaults.
- `config.toml` is gitignored. Reads fall back to `config.toml.example` (CI has no `config.toml`); `save_config` always writes `config.toml`.

## Subsystems

One paragraph each. Follow the link for the full behavior.

- **[Unified dispatch](docs/architecture.md#unified-v1-dispatch)**: `_peek_model_alias` reads `body["model"]` from the cached body; `_route_to_azure` / `_route_to_bedrock` decide. Each base URL has its own fallback domain. `/v1/responses` has no Bedrock dispatch.
- **[Auth](docs/architecture.md#authentication)**: API key via `Authorization: Bearer` or `x-api-key`. Web UI: oauth2-proxy → nginx `auth_request` → JWT (RS256, key reloaded on mtime). Admin = `"admin"` in JWT scopes, not `user.is_admin`. Disabled accounts raise `AccountDisabledError`, which renders HTML or JSON 403 based on `Accept`; admins bypass.
- **[vLLM proxy](docs/architecture.md#vllm-proxy-appservicesvllm_proxypy)**: eight `vllm_forward_*` methods sharing `_resolve_model` (exact → type fallback → any alive). One request-time failover on connect failure or 502/503/504 (connect failures `mark_down()` the server). `native_messages` routes pass Anthropic bodies through natively after `normalize_anthropic_messages` + `sanitize_native_messages_body`. `systemone` (decider) and `render` (template preview, decoded by default) have their own sections.
- **[Azure](docs/architecture.md#azure-openai-proxy-appservicesazure_proxypy)**: every LLM/VLM call goes to the v1 Responses API. Sampling knobs are stripped on chat/messages (not on `/azure/v1/responses`), `max_output_tokens` is raised to at least 16, and orphan `function_call`s are dropped. Mid-stream errors are surfaced, with rate limits mapped to `overloaded_error`. Optional `AZURE_HTTP_PROXY` / `AZURE_INSECURE` client.
- **[Bedrock](docs/architecture.md#aws-bedrock-proxy-appservicesbedrock_proxypy)**: calls go to Converse, except Messages requests for a Claude entry with `native_messages = true`, which go to bedrock-runtime's `/anthropic/v1/messages` (first-party body shape, SSE, relayed by the shared `_relay_native_anthropic_sse`) so prompt caching and thinking replay survive. Converse streams are binary AWS event-stream (`aws_eventstream.py`), not SSE. Auth is IAM keys (SigV4, `aws_sigv4.py`) or a long-term API key as Bearer; region and the IAM pair can be shared by every model via `.env` (`BEDROCK_REGION`, `BEDROCK_AWS_*`), an entry's own value winning. Roles are merged to alternate. A sampling field a model rejects is dropped and the request retried (`_send_converse`), so new families need no code. Claude effort: 4.6+ model IDs get adaptive thinking + `output_config.effort` (and 4.7+ never get `temperature`/`top_p`); older ones a thinking budget.
- **[API IP allowlist](docs/architecture.md#api-ip-allowlist-appservicesip_allowlistpy)**: admin *IP Allowlist* card. `[app].ip_allowlist_mode` `off` (default) / `monitor` (log with account, address, reason) / `enforce` (403), checked in API-key auth. Rules in `ip_allow_rules`: CIDR × who (accounts and / or org codes; none = everyone) × window (optional start, optional end = permanent; Asia/Taipei in the form). A request needs one active rule covering its address and its account. Only admins add, edit or end rules; users have no self-service. Per-worker snapshot, reloaded every 15 s and after each change; a preset end time is exact.
- **[Guardrail](docs/architecture.md#guardrail-appservicesguardrailpy)**: `[guardrail]` (admin *Guardrail* card) screens the newest user turn of local chat / responses / messages requests with Qwen3Guard-Gen. Runs only when enabled + base URL. Policy: threshold (unsafe / controversial), per-category `block` / `flag` / `ignore`, accounts, exempt users, endpoints; action `monitor` (default; guard runs in the background, no added latency) or `block` (waits for the verdict; 400). Fails open; guard tokens not billed; verdict → Langfuse `guardrail` / `guardrail_action` scores and `guardrail_*` metadata. Test connection on the card.
- **[Client rules](docs/architecture.md#client-rules-appservicesclient_checkspy-client_rulespy-mailerpy)**: admin *Clients* tab. The checks are code (`client_checks.CHECKS`), each with a violation id: `CC001` auto mode waiting for a server-side check (on by default), `CC002` plain `http://`, `CC003` outdated Claude Code, `CC004` a model the gateway does not have, `CC005` a cloud model without access. Thresholds are constants in that file, and so is each check's stage: active, `deprecated` (recorded and shown, no reminder or mail) or `retired` (not evaluated; listed with its reason). The card shows each check's last violation and suggests retiring one that has been quiet for 30 days. Per check an admin sets on / off, action (`notice` / `remind`), wording, patch and mail (`client_rule_settings`; no row = the code's defaults). A violation goes to `client_violations` under the check's id, hourly at most; for 15 days after its last one an account sees the notice on `/dashboard` with the patch as text and as a download (`.bat` for Windows, `.sh` for Linux / macOS), until it presses *I've applied it* (the notice then returns only if it violates again). A patch is environment variables only (the `env` block of `~/.claude/settings.json`, backup kept), with a base for everyone plus what Azure and AWS accounts get on top. `remind` answers the first violating request of each day with the message as a 400. Mail (Exchange EWS like AuthCenter, `<username>@<COMPANY_EMAIL_DOMAIN>`, `.env` only) goes out by an admin's click (which queues: per check, or *Mail everyone* for all checks at once), by a check's automatic mail with an optional weekly / monthly reminder, or by the card's *Monthly reminder* switch (everyone with something open, on the 1st), always through the `client_rule_mail` job in batches (20 every 10 min, 2 s apart by default), one mail per account covering everything it has open with one combined patch and a link straight to its download (the dashboard offers the same single download, one notice or several, and says what the script cannot fix); each check's form has *Send test mail* (that check alone; address and audience selectable), and the card's *Test the combined mail* sends the mail about every rule that is on, with the merged patch. Every attempt is kept in the *Mail log* under the rules (`client_mail_log`: address, checks, why, sent or failed with the error; filter and search). Claude Code versions per account come from the User-Agent (`client_versions`). Apart from the checks, the dashboard's *My API Key* window offers the account's key as a patch (`/dashboard/api-key/patch.{bat,sh}`: sets `ANTHROPIC_AUTH_TOKEN`, removes the older `ANTHROPIC_API_KEY`): what to run after regenerating it.
- **[Rate-limit fallback](docs/architecture.md#rate-limit-fallback-appservicesrate_limit_fallbackpy)**: cloud entries may chain `rate_limit_fallback` on 429 (up to 3 hops). Azure streams are read ahead for up to 5 s to catch an in-stream rate-limit event.
- **[Anthropic adapter](docs/architecture.md#anthropic-messages-api-appservicesanthropic_adapterpy)**: stateless request/response translation and `AnthropicStreamTranslator`. 10 s pings, 300 s max idle, 280 s non-stream timeout (below nginx's 300 s). `count_tokens` uses vLLM `/tokenize`, falling back to chars/4.
- **[Reasoning effort](docs/architecture.md#reasoning-effort-compatibility-appservicesreasoning_effortpy)**: per-model `reasoning_efforts` / `reasoning_effort_map`, applied at each backend's outgoing body; edited in Admin → Model Config.
- **[Cost and budgets](docs/architecture.md#cost-calculation-budgets-cloud-budget-fallback)**: price lookup is per-model → per-type → default, with an optional cached-input rate. `usage_logs.backend` splits spend. One cloud cap bounds Azure + Bedrock together: the user's own, else the `[app]` default. 429s carry `Retry-After` until local midnight.
- **[Concurrency limit](docs/architecture.md#per-user-concurrency-limit-appservicesconcurrencypy)**: `[app].concurrency_limit_mode` (`off` / `monitor` / `enforce`) + `concurrency_limit` (≥ 1; "unlimited" is `off`, never `0`). Leases live in `concurrency_leases`, taken by `deps.limited_*` on chat/responses/messages only. The heartbeat renews leases and sweeps those of dead workers, including once at startup. Admins and `users.concurrency_waived` are exempt; app accounts (`app_*`, `schema.is_app_account`) are created waived, and migration `e4b7c2d91a58` waived the existing ones.
- **[Health and metrics](docs/architecture.md#runtime-patterns-http-clients-health-loop-logging-export)**: 30 s loop on a dedicated client, with hysteresis (2 failures to go DOWN). Scrapes vLLM `/metrics` with an **exact** metric-name match (vLLM ≥ 0.20's `*_waiting_by_reason` would double-count). `PoolTimeout` keeps the previous state.
- **[Observability](docs/architecture.md#observability-appservicesobservabilitypy)**: one Langfuse generation per billable request, emitted from `_log_usage`. Errors are recorded via `_log_error`. Request headers are captured by `RequestMetaMiddleware` (pure ASGI). Phase timing (gateway overhead, upstream TTFB, TTFT, tok/s) comes from httpx event hooks plus the stream pumps, under backend-neutral names. I/O capture (`LANGFUSE_CAPTURE_IO`) records the endpoint's own shape.
- **[Prometheus metrics](docs/architecture.md#prometheus-metrics-appservicesmetricspy)**: opt-in `METRICS_ENABLED`; `GET /metrics` (404 when off). Multiprocess mode, one directory per server run under `METRICS_DIR`, summed over workers. Recorded at `_log_usage`, `_log_error`, the 429 sites in `deps.py`, the health loop and `InFlightMiddleware`.
- **[Logging](docs/architecture.md#error-log-redaction-appservicesredactpy)**: per-worker log files. `Slow request` / `Slow response headers` warnings above `SLOW_REQUEST_WARN_S`.
- **[Admin Model Config](docs/architecture.md#admin-model-config-page-apptemplatesadmin_modelshtml)**: master–detail editor over `GET/PUT /admin/api/config`. Selection lives in the URL hash; dirty tracking compares JSON snapshots. Local entries have *Test connection* (`POST /admin/api/test-model`: `GET base_url/models`, checks `real_model` is served). The list folds by backend and type, filters (edited / problems / hidden) and is keyboard-driven; *Display order* arranges `[display_order]` by drag and drop.
- **[Admin Users tab](docs/architecture.md#admin-users-tab-apptemplates_admin_user_tablehtml)**: Users / Apps tables from one partial; search, sort (`spend` = this month), status filter and paging swap one panel via `GET /admin/user-table`, state kept in the `/admin?…#users` URL. Row actions are `data-action` forms handled in place (JSON replies, `gwConfirm`, `gwToast`). The *Special access* strip above them counts each non-default permission (users and apps apart) and links to its `status` filter.
- **[Admin Model Config](docs/architecture.md#admin-model-config-page-apptemplatesadmin_modelshtml)**: master–detail editor over `GET/PUT /admin/api/config`. Selection lives in the URL hash; dirty tracking compares JSON snapshots.
- **[Daily usage rollup](docs/architecture.md#daily-usage-rollup-appservicesusage_rolluppy)**: closed local days of `usage_logs` are summed into `usage_daily` (one row per day × user × backend × model × model_type × endpoint, plus `empty_turns`). Every worker runs `rollup_loop` from the lifespan (`USAGE_ROLLUP_INTERVAL_S`, default 600, `0` off), one day per transaction under `pg_try_advisory_xact_lock`, so exactly one worker rolls each day and no external scheduler is needed; days are rolled 15 min after they end, and the first run backfills. Reads go through `aggregate`: up to the watermark from `usage_daily`, the rest from `usage_logs`. `scripts/rollup_usage_daily.py` inspects and repairs (`--recompute`).
- **[In-gateway jobs](docs/architecture.md#in-gateway-jobs-appservicesschedulerpy)**: no systemd timers. `job_loop` per job per worker, ~60 s ticks; `run_if_due` claims with a conditional UPDATE on `scheduled_jobs` (`last_started_at <= now - interval`), so each job runs once per interval across workers and hosts, and records `last_status` / `last_detail`. Jobs: anomaly scan (hourly, `ANOMALY_SCAN_INTERVAL_S`), usage-log retention (daily, off unless `USAGE_LOG_RETENTION_DAYS`) and client-rule mail (a batch every 10 min, `CLIENT_RULE_MAIL_INTERVAL_S` / `_BATCH` / `_PAUSE_S`, idle while mail is not configured). `setup.sh` removes the old scan / cleanup timers.
- **[Audit log](docs/architecture.md#audit-log-appservicesauditpy)**: `AuditMiddleware` writes one `audit_log` row per write under `/admin` / `/dashboard` (any outcome), per full API key shown and per export: actor, route template, status, client, target account (looked up before the handler), redacted request fields and JSON reply, handler notes. After the response, in a thread, never failing the request. Append-only (PG triggers). Admin *Security* → *Audit Log* card, JSON API and CSV.
- **[Database](docs/architecture.md#database)**: `users`, `usage_logs`, `usage_daily` + `usage_rollup_state`, `scheduled_jobs`, `app_owners`, `anomaly_events`, `concurrency_leases`, `ip_allow_rules`, `client_rule_settings` + `client_violations` + `client_versions` + `client_mail_log`, `audit_log`. The hourly anomaly scan is detection only, never blocking. Usage-log retention ships off on purpose.

## Testing

Tests use in-memory SQLite with `StaticPool` (all connections share one DB), set up in `tests/conftest.py`:

- `os.environ["DATABASE_URL"] = "sqlite://"` is set before any app import.
- The `_patch_all` autouse fixture patches the routing/pricing maps, every httpx client getter, every module-level `engine` (including `app.services.concurrency.engine`, `app.services.usage_rollup.engine`, `app.services.scheduler.engine` and `app.services.client_rules.engine`), `is_alive`, and the JWT decoder.
- The `client` fixture builds a test app with a no-op lifespan (no health loop, no lease heartbeat, no rollup or job loops) and mounts every router. Tests run the rollup and jobs explicitly (`usage_rollup.advance(db_session, now=...)`, `scheduler.run_if_due(job)`). Use it with `auth_header()` (API key) or `web_auth_header(sub=..., scopes=["admin"])` (JWT).
- Mock downstreams on `client.__httpx_mock__.post` (non-stream) or `.send` (stream; `FakeStreamResponse`, `FakeBedrockStreamResponse`).

Pitfalls:
- **Never let a test trigger a real `save_config()`.** It writes `config.toml` and `reload_config()` mutates the patched `TEST_*` dicts in place, emptying them for every later test. Wrap happy-path `PUT /admin/api/config` in `with patch("app.routers.admin.save_config"):` (pattern: `tests/test_models_endpoint.py::TestAdminConfigMetadataValidation`). `TestAzureFallback` in `test_azure_api.py` deliberately mutates `TEST_AZURE_MODELS`; keep the autouse patch pointing at the same dict.
- The shared httpx mock's `reset_mock()` does **not** clear `side_effect`, and some tests replace its methods. Use `patch.object(client.__httpx_mock__, "post", side_effect=...)` and assert on the mock you patched, never on the shared one.
- Import `app.routers.*` inside test functions, never at a test module's top level. `_build_test_app` imports the routers under its config patches; a collection-time import binds them to the real config and the page silently renders the wrong models.
- Walk routes with `fastapi.routing.iter_route_contexts(app.routes)` (full path, methods, dependant incl. router-level dependencies). FastAPI ≥ 0.16x keeps included routers nested, so a walk over `app.routes` finds no API routes and passes vacuously; give such a test a positive assertion (`test_every_cookie_authenticated_write_is_under_a_guarded_prefix`).
- The concurrency limit defaults to `off`. Tests that exercise it patch `app.core.deps.get_concurrency_settings`.
- SQLite ignores `FOR UPDATE`. `test_pg_concurrent_acquire_respects_limit` runs against PostgreSQL when `CONCURRENCY_TEST_PG_URL` is set; it is skipped in CI.

## Database and migrations

- Production is PostgreSQL. Migrations use PostgreSQL-only DDL, so verify them against a real PostgreSQL (a throwaway `initdb` cluster works; e.g. `/usr/lib/postgresql/16/bin` when installed), never SQLite. Check upgrade → downgrade → upgrade, then `alembic check` for model drift.
- Migrations that touch `users` start with `SET LOCAL lock_timeout = '5s'` and add columns with a constant `server_default` (metadata-only on PG ≥ 11), so they are safe under live traffic.
- Deploy order: `alembic upgrade head`, then restart.
- `usage_logs` is the billing and audit record. Retention cleanup is a deliberate governance decision, never an installer default.

## CI

`.github/workflows/ci.yml`: `uv sync --locked --dev` → `ruff check .` → `pytest tests/ -q` on Python 3.11 for pushes to `main` and every PR. `--locked` fails a PR that edits `pyproject.toml` without re-running `uv lock`. `.github/workflows/security.yml` runs `pip-audit` on the locked runtime dependencies and gitleaks on new commits (whole history weekly). Every `--ignore-vuln` there carries its reason; add none without one, and drop it when the fix ships. Fake keys belong under `tests/` or in `*.example` files, which `.gitleaks.toml` allowlists; docs write a key as `sk-your-api-key` (its one stopword).
