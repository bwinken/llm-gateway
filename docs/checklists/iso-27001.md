# ISO/IEC 27001:2022 Annex A

每個控制項先寫它要求什麼，再說明這個 gateway 現在的狀態、證據在哪裡、還缺什麼。標記說明見 [README](README.md)。

**關於文字來源**：

- 控制項的**編號與英文名稱**是 ISO/IEC 27001:2022 Annex A 的正式名稱。
- 「要求」那一行是**我寫的中文摘要，不是標準原文**。ISO 標準有著作權、需要購買，這裡不能照抄條文。要引用原文（例如寫進給內稽的文件）時，請從你們持有的標準複製；正式的中文譯本是 CNS 27001:2023。
- 英文名稱是憑記憶寫的，交出去之前請對照標準核對一次。

**範圍**：這個 gateway 與它的部署。條文 4 ~ 10（管理系統本身：範圍、風險評鑑、適用性聲明、內稽、管理審查）是組織層級，不在這裡。

## A.5 組織控制

### A.5.3 Segregation of duties　職務區隔　🟡

- **要求**：互相衝突的職務與責任範圍要分開，避免一個人可以獨自完成並掩蓋不當操作。
- **現況**：admin 可以做所有事（改設定、看任何人的 key、改額度、編輯 IP allowlist），沒有雙人覆核。補償控制是稽核紀錄：admin 的每個寫入、每次顯示完整 key、每次匯出都會記錄，而且 admin 自己改不了也刪不掉。
- **證據**：`audit_log`（`app/services/audit.py`）；PostgreSQL trigger 拒絕 UPDATE / DELETE / TRUNCATE。
- **缺口**：沒有人定期檢視稽核紀錄。寫進 AUD-3 作為風險與補償控制；檢視頻率寫進 AUD-2。

### A.5.9 Inventory of information and other associated assets　資產清冊　🟡

- **要求**：建立並維護資訊與相關資產的清冊，包含擁有者。
- **現況**：模型與後端集中在 `config.toml`。主機、金鑰（Azure、AWS、GPG、JWT 公鑰）、資料表與各自的負責人沒有清冊。
- **證據**：`config.toml`；`docs/architecture.md` 的 *Database* 一節列出所有資料表。
- **缺口**：AUD-4。

### A.5.14 Information transfer　資訊傳輸　🟡

- **要求**：組織內外各種傳輸方式都要有規則、程序或協議。
- **現況**：送往 Azure / AWS 走 TLS，Bedrock 請求有 SigV4 簽章。但傳出去的**內容**沒有任何檢查：公司規定哪些資料不能送雲端，gateway 無法執行這條規定。
- **證據**：`azure_proxy.py`、`bedrock_proxy.py`、`aws_sigv4.py`。
- **缺口**：GRD-1、GRD-2、GRD-3。

### A.5.15 Access control　存取控制　✅

- **要求**：依業務與資安需求，訂定並實作資訊與資產的實體及邏輯存取規則。
- **現況**：網頁以公司 SSO 登入；API 以每人一把 key 認證。雲端模型要 admin 逐帳號開啟。可以依帳號、部門、時間限制來源 IP。
- **證據**：`app/core/auth.py`、`app/core/deps.py`、`app/services/ip_allowlist.py`；`users.can_use_azure` / `can_use_bedrock`。
- **缺口**：無。IP allowlist 預設是 `off`，正式環境的模式待確認。

### A.5.16 Identity management　身分管理　🟡

- **要求**：管理身分的完整生命週期。
- **現況**：建立是自動的：第一次 SSO 登入時建帳號。給程式用的 service account 有明確標記（`users.is_service_account`）並指定擁有者，而且不能用它的名字登入。**結束**這一段沒有：人從 AuthCenter 移除後，gateway 上的帳號還在。
- **證據**：`auth._sync_user`；`tests/test_service_accounts.py`。
- **缺口**：CMP-7。

### A.5.17 Authentication information　鑑別資訊　🟡

- **要求**：鑑別資訊的配發與管理要有管理流程，包含告知人員如何妥善處理。
- **現況**：key 是 256 bit 隨機值，只有通過 SSO 才拿得到，可以自行重新產生（舊的立即失效）。每把 key 的發行時間與最後使用時間都有記錄。沒有到期日。key 在資料庫是明文（dashboard 與安裝程式要讀得回來）。
- **證據**：`schema._generate_api_key`、`schema.issue_api_key`；`users.api_key_created_at` / `api_key_last_used_at`；`tests/test_api_key_hardening.py`。
- **缺口**：CMP-3（長期未用自動停用）。明文儲存已決定風險接受 → CMP-2、AUD-3。

### A.5.18 Access rights　存取權限　🟡

- **要求**：依存取控制政策配發、審查、修改、移除存取權限。
- **現況**：配發與移除由 admin 操作，每一次都進稽核紀錄。admin 頁面的 *Special access* 列出所有非預設權限。缺的是**定期審查**，以及離職時的移除。
- **證據**：`audit_log`；`/admin` 的 Users 分頁。
- **缺口**：AUD-2、CMP-7。

### A.5.23 Information security for use of cloud services　雲端服務使用　🟡

- **要求**：雲端服務的取得、使用、管理、退出，都要依組織的資安要求建立流程。
- **現況**：使用 Azure OpenAI 與 AWS Bedrock。誰能用由 admin 逐帳號開啟，費用有每人上限，區域與金鑰在設定裡。沒有記錄的是：資料在供應商那邊保存多久、會不會被用於訓練、放在哪個區域的理由。
- **證據**：`[azure_models.*]`、`[bedrock_models.*]`；`deps.effective_cloud_limit`。
- **缺口**：AUD-4（供應商條款）、GRD-1。

### A.5.24 Information security incident management planning and preparation　事件管理的規劃與準備　⬜

- **要求**：定義事件管理的流程、角色與責任，做好準備。
- **現況**：沒有。
- **缺口**：CMP-5。

### A.5.25 Assessment and decision on information security events　資安事態的評估與決定　🟡

- **要求**：評估資安事態，決定是否歸類為資安事件。
- **現況**：有偵測：每小時的用量異常掃描、每週 guardrail 報告會列出要注意的帳號。沒有「判定這是不是事件、誰來判定」這一步。
- **證據**：`anomaly_scan.py`、`anomaly_events`；`weekly_reports.py`。
- **缺口**：CMP-5。

### A.5.26 Response to information security incidents　資安事件的回應　🟡

- **要求**：依文件化的程序回應資安事件。
- **現況**：可用的處置動作都有：停用帳號、重新產生 key、用 IP allowlist 限制來源、下架模型。沒有寫成程序。
- **證據**：admin 頁面；每個動作都進 `audit_log`。
- **缺口**：CMP-5。

### A.5.27 Learning from information security incidents　從資安事件學習　⬜

- **要求**：用事件中得到的知識強化控制。
- **現況**：沒有事後檢討的做法。
- **缺口**：CMP-5。

### A.5.28 Collection of evidence　證據蒐集　🟡

- **要求**：建立程序來識別、蒐集、取得、保存與資安事態有關的證據。
- **現況**：稽核紀錄不可修改，可匯出 CSV。用量紀錄即使帳號被刪也會保留。缺的是一次把相關證據打包的方法。
- **證據**：`audit_log`、`usage_logs`；`/admin/api/export/audit-log.csv`。
- **缺口**：AUD-1。

### A.5.29 Information security during disruption　中斷期間的資訊安全　⬜

- **要求**：規劃在中斷期間如何把資訊安全維持在適當水準。
- **現況**：還沒有備機，所以也沒有定義「切過去之後 allowlist、金鑰、log、備份是否一致」。
- **缺口**：HA-10 的驗證步驟。

### A.5.30 ICT readiness for business continuity　營運持續的 ICT 準備　⬜

- **要求**：依營運持續目標，規劃、實作、維護並測試 ICT 的準備度。
- **現況**：單台主機。有每日備份與還原演練，但沒有備援，也沒有定義可接受的停機時間與資料遺失。
- **證據**：`deploy/backup-db.sh`、`deploy/restore-drill.sh`。
- **缺口**：REL-2（訂目標）；HA 主題（等 server 集群）。

### A.5.33 Protection of records　紀錄保護　✅

- **要求**：保護紀錄不遺失、毀損、竄改、未經授權存取或外洩。
- **現況**：稽核紀錄在資料庫層擋掉修改與刪除。刪除帳號時用量紀錄保留。備份以公鑰加密，gateway 主機上沒有私鑰。
- **證據**：migration `07899844c700` 的 trigger；`TestDeleteUser`；`backup-db.sh`。
- **缺口**：無。

### A.5.34 Privacy and protection of PII　隱私與個資保護　🟡

- **要求**：依法規與合約要求，識別並滿足個資保護的要求。
- **現況**：gateway 自己保存的個資很少：帳號名稱、部門代碼、稽核紀錄裡的來源 IP。prompt 內容預設不保存（log 只記形狀，Langfuse 的內容擷取預設關閉）。但 prompt 裡的個資會原樣送給模型，包括雲端。
- **證據**：`redact.summarize_body`；`LANGFUSE_CAPTURE_IO`。
- **缺口**：GRD-1；CMP-6（保存期限表）。

### A.5.36 Compliance with policies, rules and standards for information security　遵循性　🟡

- **要求**：定期審查是否遵循資安政策、規則與標準。
- **現況**：程式層面的規則寫在 CLAUDE.md，大多有測試釘住，改壞了 CI 會失敗。組織層面的審查不在這裡。
- **證據**：CLAUDE.md *Rules*；`.github/workflows/ci.yml`。
- **缺口**：持續維護這份清單（CMP-1）。

### A.5.37 Documented operating procedures　文件化的操作程序　🟡

- **要求**：資訊處理設施的操作程序要寫成文件，並提供給需要的人。
- **現況**：安裝部署、容器化與搬遷、備份與還原都有文件。缺故障排除、切換、事件處理。
- **證據**：`deploy/README.md`、`deploy/migration/README.md`。
- **缺口**：REL-6、HA-10、CMP-5。

## A.6 人員控制

### A.6.3 Information security awareness, education and training　認知、教育與訓練　🟡

- **要求**：人員要接受適當的資安認知教育與訓練，並定期更新。
- **現況**：有使用指南。client rules 會在使用者的設定不安全時，在 dashboard、終端機、信件裡提醒並提供修正方式。
- **證據**：`docs/client-guide.md`；`client_checks.py`（CC001 ~ CC005）。
- **缺口**：「哪些資料可以送哪個模型」的訓練屬於組織層級。

### A.6.5 Responsibilities after termination or change of employment　離職或調職後的責任　⬜

- **要求**：離職或調職後仍然有效的資安責任要定義、執行並告知。
- **現況**：人離職後，gateway 上的帳號與 API key 仍然有效，直到 admin 手動停用。
- **缺口**：CMP-7。

### A.6.8 Information security event reporting　資安事態通報　⬜

- **要求**：提供管道，讓人員及時通報觀察到或懷疑的資安事態。
- **現況**：沒有固定的回報入口。
- **缺口**：CMP-11。

### A.6 其餘與 A.7 實體控制：組織層級

A.6.1 Screening、A.6.2 Terms and conditions of employment、A.6.4 Disciplinary process、A.6.6 Confidentiality or non-disclosure agreements、A.6.7 Remote working，以及 A.7.1 ~ A.7.14 全部，都是人資與機房的範圍。

和 gateway 有關的只有兩點：做備援時兩台主機不能在同一個實體位置與儲存上（A.7.5、A.7.11 → HA-1）；存過資料庫與備份的磁碟報廢時要銷毀（A.7.14）。

## A.8 技術控制

### A.8.2 Privileged access rights　特權存取權　🟡

- **要求**：限制並管理特權存取權的配發與使用。
- **現況**：admin 權限只來自 AuthCenter token 裡的 `admin` scope，而且只在網頁上有效，API key 不帶任何管理權限。資料庫裡舊的 `is_admin` 欄位已經停用。admin 每次查看完整 key 都會留紀錄。
- **證據**：`auth.get_web_user`；`tests/test_admin_flag_retired.py`；`GET /admin/users/{id}/api-key`。
- **缺口**：誰有 admin 的名單在 AuthCenter，審查時要一起看 → AUD-2。

### A.8.3 Information access restriction　資訊存取限制　✅

- **要求**：依存取控制政策限制對資訊與資產的存取。
- **現況**：每個帳號只看得到自己的用量與有權限的模型。沒有權限的雲端模型不會出現在模型清單裡。service account 的 key 只有擁有者在 dashboard 看得到，API 端點不回傳任何 key。
- **證據**：`model_catalog`；`tests/test_status_usage.py`（`test_an_apps_key_is_never_returned`）。
- **缺口**：無。

### A.8.5 Secure authentication　安全鑑別　🟡

- **要求**：依存取限制與政策，實作安全的鑑別技術與程序。
- **現況**：網頁走 SSO，JWT 以 RS256 驗證。API key 256 bit。同一個來源送出太多不同的錯誤 key 會被鎖住。用 SSO token 換 key 的端點另有 throttle、IP 檢查與稽核。
- **證據**：`auth._decode_jwt`；`auth_throttle.py`（`TestThrottle`）；`tests/test_auth_exchange.py`。
- **缺口**：throttle 是每個 worker 各自計數（HA-5，多台時才有影響）。

### A.8.6 Capacity management　容量管理　🟡

- **要求**：依目前與預期的容量需求，監控並調整資源的使用。
- **現況**：可以限制每人的併發數（預設關閉）。連線池使用率每 30 秒記錄一次，超過 80% 寫警告。看得到每台 vLLM 的執行中與排隊數。沒有壓測，不知道單台的上限。
- **證據**：`concurrency.py`；`server_state.pool_snapshot`；`health.py`。
- **缺口**：REL-3。

### A.8.8 Management of technical vulnerabilities　技術弱點管理　🟡

- **要求**：取得使用中系統的技術弱點資訊，評估暴露程度並採取措施。
- **現況**：Python 相依套件每個 PR、每次 push、每週掃描；dependabot 自動開更新 PR；每個被忽略的弱點都要寫理由。容器基底映像與 OS 套件沒有掃描。
- **證據**：`.github/workflows/security.yml`；`.github/dependabot.yml`。
- **缺口**：CMP-9。

### A.8.9 Configuration management　組態管理　🟡

- **要求**：硬體、軟體、服務、網路的組態（含安全組態）要建立、文件化、實作、監控並審查。
- **現況**：模型與系統設定透過 admin 頁面修改，存檔前驗證，並寫入稽核紀錄。但稽核只記「哪些欄位變了」，不記改前改後的值，也沒有舊版本可以回復。`.env` 的變更沒有紀錄。
- **證據**：`PUT /admin/api/config`、`config_changes`。
- **缺口**：CMP-4；REL-5（至少先有備份）。

### A.8.10 Information deletion　資訊刪除　🟡

- **要求**：不再需要的資訊要刪除。
- **現況**：應用程式 log 保存 14 天。用量明細有保存期限的功能，但預設關閉，目前永久保存。Langfuse 與備份的期限各自設定，沒有統一的表。
- **證據**：`usage_retention.py`、`USAGE_LOG_RETENTION_DAYS`；`LOG_RETENTION`。
- **缺口**：CMP-6（已決定明細保存 1 年）。

### A.8.11 Data masking　資料遮罩　🟡

- **要求**：依存取控制政策與法規要求使用資料遮罩。
- **現況**：系統自己的敏感資料有遮罩：admin 列表上的 key 只顯示頭尾，log 裡的請求只記形狀，稽核紀錄會遮蔽機密欄位。使用者 prompt 裡的個資沒有遮罩。
- **證據**：`mask_api_key`；`redact.summarize_body`；`audit.redact`。
- **缺口**：GRD-1。

### A.8.12 Data leakage prevention　資料外洩防護　⬜

- **要求**：對處理、儲存、傳輸敏感資訊的系統、網路與裝置，採取防止資料外洩的措施。
- **現況**：沒有。使用者可以把任何內容送給任何有權限的模型，包括雲端。唯一的管控是「誰能用雲端」。
- **缺口**：GRD-1、GRD-2。這是公司雲端資料規定目前無法落實的原因。

### A.8.13 Information backup　資訊備份　🟡

- **要求**：依備份政策維護資訊、軟體與系統的備份，並定期測試。
- **現況**：資料庫每日線上備份，備份後驗證、以公鑰加密，保留 30 份每日與 12 份每月，可以再複製到另一台。還原演練有腳本，每次都留紀錄。設定檔不在備份裡。
- **證據**：`deploy/backup-db.sh`；`deploy/restore-drill.sh`、`restore-drill.log`。
- **缺口**：REL-5（設定檔）。異地複製（`BACKUP_COPY_TO`）是否有設定、多久演練一次 → 待確認。

### A.8.14 Redundancy of information processing facilities　資訊處理設施的備援　⬜

- **要求**：資訊處理設施要有足夠的備援以滿足可用性要求。
- **現況**：gateway 與資料庫都只有一台。下游有部分備援：同類型的 vLLM 主機之間會自動 failover。
- **證據**：`vllm_proxy._post_with_failover`。
- **缺口**：HA 主題（等 server 集群）。

### A.8.15 Logging　日誌　🟡

- **要求**：產生、保存、保護並分析記錄活動、例外、錯誤與其他相關事件的日誌。
- **現況**：三種紀錄：管理操作（`audit_log`，不可修改）、每個模型請求（`usage_logs`：誰、何時、哪個模型、用量）、應用程式 log。log 沒有集中收集，只在主機上。
- **證據**：`audit.py`；`vllm_proxy._log_usage`；`app/core/logger.py`。
- **缺口**：是否送到公司的 log 平台或 SIEM → 待確認。

### A.8.16 Monitoring activities　監控活動　🟡

- **要求**：監控網路、系統與應用程式的異常行為，並採取適當行動評估可能的資安事件。
- **現況**：有偵測、沒有通知。每小時掃描用量異常；提供 Prometheus 指標；慢請求寫警告；每週有用量與 guardrail 報告。但沒有任何告警規則，出事時不會有人被通知。
- **證據**：`anomaly_scan.py`；`metrics.py`；`weekly_reports.py`。
- **缺口**：REL-1。

### A.8.19 Installation of software on operational systems　作業系統上的軟體安裝　🟡

- **要求**：以程序與措施安全地管理正式系統上的軟體安裝。
- **現況**：相依套件版本完全鎖定，CI 與映像建置都用鎖定版本；容器以非 root 執行。誰在何時部署了哪個版本，沒有紀錄。
- **證據**：`uv.lock`；`deploy/migration/Dockerfile`。
- **缺口**：部署紀錄 → 待確認現行做法。

### A.8.20 Networks security　網路安全　🟡

- **要求**：保護、管理並控制網路與網路裝置，以保護系統與應用程式中的資訊。
- **現況**：gateway 只聽本機位址，對外只有 nginx。可以用 IP allowlist 限制 API 的來源。主機防火牆屬於組織層級。
- **證據**：`deploy/llm-gateway.service`（`--host 127.0.0.1`）；`ip_allowlist.py`。
- **缺口**：無（程式面）。

### A.8.21 Security of network services　網路服務安全　🟡

- **要求**：識別、實作並監控網路服務的安全機制、服務水準與要求。
- **現況**：對外 TLS 1.2 / 1.3。HSTS 還沒開。gateway 到 vLLM 主機是否走明文 http 取決於設定。
- **證據**：`deploy/llm-gateway-example.nginx.conf`。
- **缺口**：CMP-10（HSTS）。待確認：到 vLLM 的連線、`AZURE_INSECURE` 沒有開。

### A.8.24 Use of cryptography　密碼學使用　🟡

- **要求**：定義並實作有效使用密碼學的規則，包含金鑰管理。
- **現況**：傳輸有 TLS；備份用 GPG 公鑰加密；Bedrock 請求有 SigV4 簽章；JWT 用 RS256。靜態資料沒有加密：API key 在資料庫是明文，Azure / AWS 的金鑰在 `config.toml` 是明文（admin 介面不會顯示）。
- **證據**：`backup-db.sh`；`aws_sigv4.py`；`config.SECRET_FIELDS`。
- **缺口**：CMP-2（下游金鑰加密存放；API key 明文已決定風險接受）。

### A.8.25 Secure development life cycle　安全開發生命週期　🟡

- **要求**：建立並套用軟體與系統安全開發的規則。
- **現況**：每個 PR 跑 lint、測試、相依套件鎖定檢查、弱點與機密掃描。容易出事的規則寫在 CLAUDE.md，並有測試釘住。
- **證據**：`.github/workflows/`；CLAUDE.md。
- **缺口**：CMP-8（測試環境）、CMP-9（SAST）。

### A.8.26 Application security requirements　應用程式安全要求　🟡

- **要求**：開發或取得應用程式時，識別、明訂並核准資安要求。
- **現況**：安全要求寫成規則並對應到測試（CLAUDE.md 的 *Security and logs* 一節）。沒有正式的核准流程。
- **缺口**：無（程式面）。

### A.8.27 Secure system architecture and engineering principles　安全架構與工程原則　✅

- **要求**：建立、文件化、維護安全系統工程的原則，並用於所有開發活動。
- **現況**：架構文件完整。關鍵的設計選擇都寫明理由：哪些地方失敗時放行（計費、guardrail、併發計數）、哪些地方拒絕（認證、額度）。
- **證據**：`docs/architecture.md`；CLAUDE.md。
- **缺口**：無。

### A.8.28 Secure coding　安全程式撰寫　🟡

- **要求**：軟體開發採用安全程式撰寫原則。
- **現況**：瀏覽器端的防護完整：CORS 不帶 credentials、跨站寫入會被擋、頁面輸出一律跳脫、admin 可編輯的連結只接受 http(s)。client 看不到內部錯誤細節。沒有靜態分析工具。
- **證據**：`browser_security.py`（`tests/test_browser_security.py`）；`TestClientSeesNoInternals`。
- **缺口**：CMP-9。

### A.8.29 Security testing in development and acceptance　開發與驗收的安全測試　🟡

- **要求**：在開發生命週期中定義並實作安全測試流程。
- **現況**：安全相關的行為有單元測試（認證、throttle、跨站防護、key 不外洩、IP allowlist）。沒有滲透測試。
- **證據**：`tests/test_api_key_hardening.py`、`test_auth_exchange.py`、`test_browser_security.py` 等。
- **缺口**：CMP-9；滲透測試由資安單位安排。

### A.8.31 Separation of development, test and production environments　環境分離　⬜

- **要求**：開發、測試與正式環境要分開並受保護。
- **現況**：自動化測試用記憶體內的資料庫，不碰正式環境。但沒有 staging：改動通過 CI 後直接上正式環境。
- **缺口**：CMP-8（等 server 集群）。

### A.8.32 Change management　變更管理　🟡

- **要求**：資訊處理設施與資訊系統的變更要經過變更管理程序。
- **現況**：程式變更走 git、PR、CI。資料庫變更走 migration，並規定要驗證升級與降級。admin 的設定變更進稽核紀錄。缺設定值的歷史。
- **證據**：`alembic/versions/`；`audit_log`。
- **缺口**：CMP-4。

### A.8.33 Test information　測試資訊　🟡

- **要求**：測試用的資訊要適當地選擇、保護與管理。
- **現況**：自動化測試只用假資料與假 key。搬遷演練會用到正式資料的複本：打包時強制加密，並剝除會對外產生作用的設定（寄信、Langfuse），演練腳本拒絕在正式主機上執行。
- **證據**：`deploy/migration/`（`ENV_STRIP_RE`、`guard_not_production`）。
- **缺口**：寫明誰可以接觸演練用的複本。

### A.8.34 Protection of information systems during audit testing　稽核測試期間的系統保護　🟡

- **要求**：稽核測試等查核活動要規劃，並與管理階層議定。
- **現況**：所有匯出都是唯讀，而且每次匯出都會記錄。
- **證據**：`audit._AUDITED_READS`。
- **缺口**：AUD-1。
